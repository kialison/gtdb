Use the Event Markets WebSocket to receive account updates as orders change, trades are matched or confirmed, positions change, and settlements become available.

<Note>
  Public market-data channels do not require authentication. The channels on this page are private and require API Key authentication.
</Note>

## Connect

```text
wss://broker.dexbuilder.com/v4/ws/event_markets
```

This endpoint implements the broker WebSocket v2 JSON protocol. Client requests use the op field; server responses include op, ch, result, and err. Include a client-generated id when you need to correlate an ACK or error with a request.

## Authenticate a private subscription

Authenticate inline on the first private request:

```json
{
  "t": 1787026512123,
  "id": "orders-1",
  "op": "subscribe",
  "ch": "em.orders",
  "payload": {
    "all": true
  },
  "auth": {
    "method": "api_key",
    "key": "<api_key>",
    "sign": "<signature>"
  }
}
```

For subscribe and unsubscribe, sign this exact message with HMAC-SHA512 and hex-encode the result:

```text
channel=<channel>&event=<operation>&time=<timestamp_ms>
```

The time value is the outer request t. The API Secret is used locally to create the signature and is never sent over WebSocket.

Python signing example:

```python
import hashlib
import hmac

channel = "em.orders"
operation = "subscribe"
timestamp_ms = 1787026512123
message = f"channel={channel}&event={operation}&time={timestamp_ms}"

signature = hmac.new(
    b"<api_secret>",
    message.encode("utf-8"),
    hashlib.sha512,
).hexdigest()
```

You may pre-authenticate once per connection with server.sign:

```json
{
  "t": 1787026512123,
  "id": "auth-1",
  "op": "auth",
  "ch": "server.sign",
  "payload": {
    "method": "api_key",
    "key": "<api_key>",
    "sign": "<signature>"
  }
}
```

For server.sign, sign the decimal string representation of the outer t:

```text
HexEncode(HMAC-SHA512(api_secret, decimal(t)))
```

## Subscribe to account updates

Private subscriptions accept either:

- payload.items: an array of filter objects. Each filter contains a condition_id.
- payload.all: true: all account updates available to the authenticated user.

The two forms are mutually exclusive. A request accepts up to 100 items, and a connection supports up to 10,000 active subscriptions.

Example for one market:

```json
{
  "t": 1787026512123,
  "id": "orders-2",
  "op": "subscribe",
  "ch": "em.orders",
  "payload": {
    "items": [
      {
        "condition_id": "gate_0xb610...901a"
      }
    ]
  }
}
```

Successful ACK:

```json
{
  "t": 1787026512150,
  "id": "orders-2",
  "trace_id": "<trace_id>",
  "op": "subscribe",
  "ch": "em.orders",
  "err": null,
  "result": {
    "status": "success",
    "message": "subscribed"
  }
}
```

To remove filters, send the same request with op set to unsubscribe. The server does not send an initial private snapshot; use the REST endpoints below to establish the initial state and recover messages missed during reconnects.

## Private channels

| Channel | Purpose | Filter |
| --- | --- | --- |
| em.orders | Order lifecycle updates | condition_id |
| em.usertrades | Trades belonging to the authenticated user | condition_id |
| em.positions | Position changes | condition_id |
| em.settlements | Settlement and claimability updates | condition_id |

### Order updates

Order results contain the public order state for the authenticated account:

```json
{
  "order_id": "123456789",
  "client_order_id": "client-order-1",
  "event_id": "gate_632804",
  "condition_id": "gate_0xb610...901a",
  "token_id": "gate_572803...39200",
  "outcome": "Yes",
  "side": "BUY",
  "order_mode": "LIMIT",
  "order_type": "GTC",
  "px": "0.45",
  "qty": "100",
  "filled_qty": "20",
  "left_qty": "80",
  "status": "OPEN",
  "created_ts": 1787026500000,
  "updated_ts": 1787026512027
}
```

| Field | Type | Description |
| --- | --- | --- |
| order_id | string | Platform order identifier. |
| client_order_id | string | Optional client-supplied identifier. |
| event_id | string | Optional event identifier. |
| condition_id | string | Market condition identifier. |
| token_id | string | Optional outcome-token identifier. |
| outcome | string | Optional outcome label. |
| side | string | BUY or SELL. |
| order_mode | string | Execution mode, such as LIMIT or MARKET. |
| order_type | string | Time-in-force or order type, such as GTC, GTD, FOK, or FAK. |
| px | string | Optional order price. |
| qty | string | Original order quantity. |
| filled_qty | string | Quantity filled so far. |
| left_qty | string | Quantity remaining. |
| status | string | PROCESSING, OPEN, CANCELLING, MATCHED, CANCELED, or FAILED. |
| error_code | string | Optional failure or rejection code. |
| created_ts | integer | Creation time in Unix milliseconds. |
| updated_ts | integer | Last update time in Unix milliseconds. |

A partially filled order normally remains OPEN; use filled_qty and left_qty to determine execution progress.

### User trades

The em.usertrades channel reports executions associated with the authenticated user. A MATCHED event may be enabled by service configuration; CONFIRMED events are always delivered.

```json
{
  "trade_id": "trade-1",
  "order_id": "123456789",
  "client_order_id": "client-order-1",
  "event_id": "gate_632804",
  "condition_id": "gate_0xb610...901a",
  "token_id": "gate_572803...39200",
  "outcome": "Yes",
  "side": "BUY",
  "role": "MAKER",
  "px": "0.45",
  "qty": "20",
  "fee_rate": "0.001",
  "status": "CONFIRMED",
  "created_ts": 1787026512027
}
```

| Field | Type | Description |
| --- | --- | --- |
| trade_id | string | User trade identifier. |
| order_id | string | Related platform order identifier, when available. |
| client_order_id | string | Related client order identifier, when available. |
| event_id | string | Related event identifier, when available. |
| condition_id | string | Market condition identifier. |
| token_id | string | Outcome-token identifier, when available. |
| outcome | string | Outcome label, when available. |
| side | string | BUY or SELL. |
| role | string | User role, MAKER or TAKER. |
| px | string | Execution price. |
| qty | string | Executed quantity. |
| fee_rate | string | Fee rate as a decimal ratio. |
| status | string | MATCHED or CONFIRMED. |
| created_ts | integer | Trade creation time in Unix milliseconds. |

For authoritative history, query GET [https://api.dexbuilder.com/api/v4/event_markets/usertrades](https://api.dexbuilder.com/api/v4/event_markets/usertrades). The REST response uses price and size, while the WebSocket result uses px and qty.

REST query parameters:

| Parameter | Type | Description |
| --- | --- | --- |
| condition_id | string | Filter by market condition. |
| from / to | integer | Inclusive time range in Unix milliseconds. |
| sort_type | string | Sort field, such as created_at or updated_at. |
| order_id | string | Filter by order. |
| token_id | string | Filter by outcome token. |
| limit | integer | Maximum number of records to return. |
| cursor | string | Cursor returned by the previous response. |

Response shape:

```json
{
  "items": [
    {
      "trade_id": "trade-1",
      "order_id": "123456789",
      "client_order_id": "client-order-1",
      "condition_id": "gate_0xb610...901a",
      "token_id": "gate_572803...39200",
      "side": "BUY",
      "role": "MAKER",
      "price": "0.45",
      "size": "20",
      "fee_rate": "0.001"
    }
  ],
  "next_cursor": "<next_cursor>"
}
```

### Positions

The em.positions result contains position quantities and settlement state. The public WebSocket contract does not include a mark-price field.

```json
{
  "position_id": "987654321",
  "event_id": "gate_632804",
  "token_id": "gate_572803...39200",
  "outcome": "Yes",
  "qty": "80",
  "avg_px": "0.45",
  "settle_status": "UNSETTLED",
  "locked_qty": "10",
  "available_qty": "70",
  "claimable_amount": "0",
  "updated_ts": 1787026512027
}
```

| Field | Type | Description |
| --- | --- | --- |
| position_id | string | Position identifier. |
| event_id | string | Related event identifier, when available. |
| token_id | string | Outcome-token identifier, when available. |
| outcome | string | Outcome label, when available. |
| qty | string | Position quantity. |
| avg_px | string | Average opening price, when available. |
| settle_status | string | Settlement state, when available. |
| locked_qty | string | Quantity locked by open orders or settlement. |
| available_qty | string | Quantity available for trading or settlement. |
| claimable_amount | string | Claimable settlement amount, when available. |
| updated_ts | integer | Last update time in Unix milliseconds. |


| Field | Type | Description |
| --- | --- | --- |
| position_id | string | Settled position identifier. |
| event_id | string | Related event identifier, when available. |
| condition_id | string | Market condition identifier. |
| winning_outcome | string | Winning outcome, when available. |
| is_winner | boolean | Whether the position won. |
| claimable_amount | string | Amount available to claim, when available. |
| created_ts | integer | Settlement creation time in Unix milliseconds. |

## REST recovery

After reconnecting, query the corresponding private REST endpoints to rebuild state and recover missed updates:

- Orders: GET [https://api.dexbuilder.com/api/v4/event_markets/orders](https://api.dexbuilder.com/api/v4/event_markets/orders)
- User trades: GET [https://api.dexbuilder.com/api/v4/event_markets/usertrades](https://api.dexbuilder.com/api/v4/event_markets/usertrades)
- Positions: GET [https://api.dexbuilder.com/api/v4/event_markets/positions](https://api.dexbuilder.com/api/v4/event_markets/positions)

## Heartbeat, errors, and reconnects

The server sends WebSocket Ping control frames. Standard clients should reply with Pong automatically. Clients may also send:

```json
{"t":1787026512123,"id":"ping-1","op":"ping"}
```

The response contains result.status: "success" and result.message: "pong".

Errors use this shape:

```json
{
  "t": 1787026512200,
  "id": "orders-2",
  "trace_id": "<trace_id>",
  "op": "subscribe",
  "ch": "em.orders",
  "err": {
    "code": 2,
    "message": "invalid subscription"
  },
  "result": null
}
```

Common codes are 1 invalid request format, 2 invalid argument, 3 server error, and 4 authentication failure. Subscriptions and missed messages are not retained after disconnect. Reconnect with backoff, authenticate again, restore subscriptions, then use REST recovery before applying new events.
